# Memory Compression and Data Generation - Idea Review

## 対象
`sleep_consolidation.py` 周辺の「記憶圧縮」と「学習用データ生成」。

## 何を解くか
- 長い会話履歴をそのまま保存すると、検索ノイズとコンテキスト汚染が増える。
- そのまま学習データにすると、誤りや偏りも一緒に増幅する。
- なので、まず記憶を圧縮し、その後に学習用データを生成する二段構えが必要。

## 先行事例
- `MemGPT` は階層メモリで情報を tier 間移動し、長い文脈を扱っている。
- `Generative Agents` は経験を保存し、reflection で高次の記憶に圧縮している。
- この案は両者の延長で、`DB1 -> DB2 -> training data` の流れに近い。

## 記憶圧縮の考え方
- 原文を捨てずに、まず構造化された「事実候補」に落とす。
- 各記憶に `source_ids`、`confidence`、`status` を持たせる。
- `confirmed` だけを長期保存し、`tentative` は保留、`conflicted` は除外する。
- 要約より抽出を優先し、元発話への参照を残す。

## データ生成の考え方
- 圧縮済みの記憶から、学習向けの `input / thought / output` を作る。
- そのまま自己生成すると危ないので、生成前にフィルタが必要。
  - 情動が大きいものを優先
  - 矛盾記憶を除外
  - 低信頼記憶を除外
  - 長すぎるものを分割
- 学習データは、元の記憶と再生成物の差分が追える形にする。

## 重要なリスク
- 自己生成ループで誤りが固定化される。
- 生成された `thought` がもっともらしくても、正解とは限らない。
- 圧縮しすぎると、後で復元できない。
- 圧縮不足だと、学習データが汚れる。

## 現実的な設計
1. `DB1` から候補を選ぶ
2. LLM で事実候補に抽出する
3. 信頼度で `confirmed` のみ残す
4. 学習データ候補を作る
5. 再フィルタして JSONL 化する
6. 最後に学習へ回す

## データスキーマ案
```json
{
  "input": "str",
  "thought": "str",
  "output": "str",
  "source_ids": ["str"],
  "confidence": 0.0,
  "status": "confirmed"
}
```

## 実現性
- 実現性: 中。
- 難易度: 中〜高。
- 工数感: 大きめ。

## 結論
- 記憶圧縮とデータ生成は分けて考えるべき。
- MVP は「圧縮の精度を上げる」ことを優先し、学習は後段に回すのが安全。
