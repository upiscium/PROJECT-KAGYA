# Dual Memory System - Risk Notes

## 対象
`impl-specs/v1.0.md` の `DualMemorySystem`。短期の episodic memory と長期の semantic memory を分ける案。

## 何がいいか
- 人間の記憶モデルに近く、説明しやすい。
- 会話ログをそのまま長期保存せず、圧縮・抽出してから残せる。
- `DB1` と `DB2` を分けることで、検索対象と保存対象を分離できる。

## 先行事例
- `MemGPT` は階層的なメモリ管理で、限られたコンテキスト窓を拡張する発想を採っている。
- `Generative Agents` は経験の蓄積・反省・再利用で、長期的なふるまいの一貫性を作っている。
- この案は両者にかなり近く、特に「記憶の圧縮」と「反映」が中心テーマ。

## 主な設計リスク
- `DB2` に上げる内容の誤判定。
  - 些細な雑談を事実化すると、長期汚染が起きる。
  - ユーザーの一時的発言を恒久ルールとして扱う危険がある。
- 検索結果の混線。
  - `DB1` は直近文脈、`DB2` は事実・ルールと役割が違うが、出力時に同じ強さで混ぜるとノイズになる。
- 圧縮の情報落ち。
  - 要約で「何が重要だったか」が消えると、後で追跡できない。
- 更新の一貫性。
  - 同じ事実が複数形式で保存されると、矛盾が増える。

## 実装上の落とし穴
- embedding 検索だけに頼ると、意味が近いだけの不要記憶を拾いやすい。
- メタデータが弱いと、`Arousal` や時系列でのフィルタが機能しない。
- `consolidate_to_semantic` で LLM 要約をそのまま真実扱いすると、幻覚を永続化する。
- 削除タイミングが早いと、DB1 から DB2 への移行失敗時にデータ損失が起きる。

## 現実的な評価
- 実現性: 高い。
- 難易度: 中。
- 相性: RAG 系、会話エージェント系と良い。
- 工数感: 小規模なら早いが、品質改善には反復が必要。

## 推奨する最小構成
- `DB1` は最近 N 件の会話と情動メタデータだけ保持する。
- `DB2` は「ユーザーの永続的嗜好」「明示されたプロフィール」「繰り返し確認された事実」だけに限定する。
- `DB2` への昇格は自動だけでなく、保守的なルールを入れる。
- まずは `retrieve_context` を「DB1 優先、DB2 補助」にする。

## 失敗しやすい指標
- 保存量が多い = 良い記憶、ではない。
- 検索ヒット率が高い = 良い応答、でもない。
- まず見るべきなのは、誤保存率と矛盾率。

## 結論
- この記憶設計は中核としてかなり有望。
- ただし成功条件は「たくさん覚えること」ではなく、「少なく正しく覚えること」。
- 次の焦点は、`DB2` 昇格条件の厳格化と、検索時の混線防止。

## リスク回避策
- 昇格条件を厳しくする。
  - 1回だけの発言では昇格しない。
  - 複数回確認された事実、明示的な自己申告、長期に有効な嗜好だけを対象にする。
- 信頼度スコアを持たせる。
  - 各記憶に `confidence` と `source` を付ける。
  - 低信頼の記憶は検索に出しても参考扱いに留める。
- 人間の確認を挟む。
  - 重要なプロフィール情報や恒久的ルールは、保存前に確認する。
  - 自動昇格は補助にとどめる。
- DB1 から DB2 へは二段階移行にする。
  - まず仮保存。
  - 次回以降も整合したら正式保存。
- 要約ではなく抽出に寄せる。
  - LLM の自由要約だけに頼らず、事実候補を構造化して残す。
  - 元発話への参照 ID を保持する。
- 破壊的削除を避ける。
  - DB1 から消す前にアーカイブ期間を置く。
  - 移行失敗時のロールバック経路を残す。
- 検索で役割を分ける。
  - DB1 は直近文脈優先。
  - DB2 は確定済み事実のみ。
  - 両者の出力を混ぜる前に優先度を付ける。
- 矛盾検出を入れる。
  - 同じユーザー属性に異なる値が入ったら警告する。
  - 矛盾が増えた記憶は自動的に降格する。
- 評価指標を決める。
  - 誤保存率、矛盾率、再利用率を追う。
  - 単純な保存件数は主要指標にしない。
